# Decision log

Each entry: the decision, why, and the alternative that was rejected.

## 1. Standard library only, no numpy

- Decision: write TF-IDF, the SVD and the search with plain Python lists and dicts.
- Why: the demo runs anywhere Python 3.11 runs, with nothing to install. With 315 records and a few hundred words, the speed is fine (the model builds in a couple of seconds).
- Rejected: numpy or scikit-learn. Faster for large data, but it hides the steps this demo wants to show, and adds an install step.

## 2. Block power iteration for the truncated SVD

- Decision: find the 32 main directions by repeating "multiply by X, multiply by X-transpose, make the columns orthogonal", with a fixed random seed and 30 steps.
- Why: it is short, it needs only sparse multiplications, and it is repeatable. We only need the space those directions span, because any rotation inside that space keeps all dot products and cosines.
- Rejected: a full eigen-decomposition of a dense matrix (slow in pure Python, more code), and a Lanczos method (more code for no gain at this size).

## 3. Documents are embedded by projection, not by stored SVD factors

- Decision: a document vector is its TF-IDF row multiplied by the 32 learned directions. A query goes through the same steps.
- Why: query and document share one code path, so there is no special "fold-in" step. The browser can rebuild the document vectors itself from the sample file plus one small model file.
- Rejected: shipping precomputed document vectors to the browser. That would duplicate the data and let it drift from the records.

## 4. Compare two ways to use the negative term, and add a third

- Decision: `score` (subtract cosines), `vector` (subtract unit-length vectors) and `vector-raw` (subtract vectors as the model gives them).
- Why: the brief asked for the first two. Doing the algebra showed that `score` and `vector` always rank alike, so the experiment says that plainly and checks it with numbers. `vector-raw` is where a real difference can appear, so it is included to show what that difference is.
- Rejected: reporting `vector` as a separate technique with a made-up difference. The honest result is that the two share an order.

## 5. The experiment prints what it finds, and nothing else

- Decision: the report is generated by code, with no timings and no random choices, and the README quotes numbers from the same run.
- Why: so a reader can run it and get the same numbers.
- Rejected: writing result numbers by hand into the README without a command that produces them.

## 6. An empty negative means "no negative"

- Decision: a negative that is empty, blank, or has no word in the vocabulary changes nothing. All three methods then return the plain scores.
- Why: a user who clears the box expects the plain search. It also avoids dividing by a zero-length vector.
- Rejected: raising an error for an empty negative, and treating an unknown negative word as a mismatch.

## 7. A query with no known word returns an empty list

- Decision: return no results, and say which words were ignored (CLI and web page).
- Why: scoring against a zero vector would give every record the same score and a meaningless order.
- Rejected: falling back to a random or alphabetical list.

## 8. Ties break by object ID

- Decision: sort by score, then by ID.
- Why: several records have the same text, so they have the same score. A fixed rule keeps the output the same on every run and in the browser.
- Rejected: relying on the sort being stable, which would depend on file order.

## 9. Small word rules, repeated in JavaScript

- Decision: lower-case, drop accents, cut one trailing "s" (not "ss"), drop a short list of common words, keep words of two or more letters. Written twice: `vectors.py` and `web/search.js`.
- Why: simple rules are easy to copy exactly. A test runs both and compares the results.
- Rejected: a real stemmer (more code to copy exactly into JavaScript), and sending the query to a Python server (the page would no longer be static).

## 10. Words that appear in only one record are dropped (min_df = 2)

- Decision: the vocabulary keeps words that appear in at least two records.
- Why: a word seen once cannot link two records, so it adds a dimension without helping the search. It also keeps the model file small (about 75 KB).
- Rejected: keeping every word. The cost is that a rare query word (for example a single unusual title) is ignored, and the tool says so.

## 11. One copy of the sample file

- Decision: the page loads `../data/sample.json`, so you serve the repo root and open `/web/`.
- Why: two copies can drift apart.
- Rejected: a copy inside `web/`, and embedding the data in the page, which would work from a plain file but double the data.

## 12. Model file is committed, and a test checks it is current

- Decision: `web/model.json` is stored in the repo. A test rebuilds the model and compares (to within 0.0001).
- Why: the page should work after a clone with no build step. The test catches a stale file.
- Rejected: building the model in the browser (the SVD is slow in JavaScript on every page load, and the page would need the whole fit code).

## 13. Fetch script keeps public-domain records only

- Decision: ask the API for `isPublicDomain=true` and check the field again on each record.
- Why: the data is CC0, but the museum notes that some listed works are under copyright. Keeping only public-domain records avoids any doubt.
- Rejected: using all records the API returns.

## 14. Data is a convenience sample, and says so

- Decision: choose records by 18 search words, not at random. `DATA.md` states this and that some types are over-represented.
- Why: it gives a mix of object types that makes "less of this" queries meaningful.
- Rejected: a random sample from the whole collection. Most random records would share few words, so the search would show little.
